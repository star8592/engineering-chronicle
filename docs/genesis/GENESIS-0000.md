## 0. 创世宣言

我们要构建的，不是另一款画软件架构图的工具，而是一套能够**记录事实、重建历史、验证结果、解释演化并安全探索未来**的软件工程基础设施。

工程开发并非一次性的代码产出，而是由需求、决策、假设、Agent 行动、人类操作、代码变更、测试证据、部署结果和运行反馈共同构成的动态过程。任何重要的工程判断都应该能回答：**为什么这样设计？谁或什么执行了改变？有什么独立证据？当时的真实状态是什么？失败是如何发生和修复的？能否在隔离环境重新验证？**

最终愿景：

- **Engineering Chronicle（工程编年史）**：可信的工程事件、证据、历史、因果与状态基础设施；建议独立立项。
- **Engineering Universe（工程宇宙）**：基于 Chronicle 的实时动态架构、可缩放数字孪生、历史时间机器和交互式产品体验。
- **Engineering Intelligence（工程智能）**：面向未来的验证、长期工程记忆、实验、优化与智能协作层。
- **ArchVerify**：早期“可执行架构与验证”的工作名称；保留为能力概念，不应与整个新产品混同。
- **Engineering Time Machine**：早期“工程回放”的能力概念，最终融入 Chronicle 的时态与回放体系。

一句话宗旨：**可信地知道过去，准确地理解现在，有边界地探索未来。**

## 1. 溯源：本次对话的真实思想演化

以下 E00–E06 按会话发言顺序重建；属于本次讨论的概念历史索引，**不是运行系统已经采集的加密日志**。

### E00 — 起点：发现 Archify/Archifyi

**用户触发：**“https://archifyi.com/ 这是个什么”。

最初研究将其视为 AI 辅助软件架构图生成与可视化方向的例子，重点不是依赖其网站，而是关注“架构模型可成为 AI 开发系统的公共交互载体”。讨论认为可能复用开源架构图思路，但是否采用特定 Archify 项目、协议和许可证，实施前必须逐项核实。

**演化意义：**从静态文档/代码浏览转向可交互的工程架构呈现。

### E01 — 用户提出验证突破

**用户原话：**“我觉得可以在这个思路基础上延伸：Archify 是可视化工具，是代码验证器。它能凭一张架构图证明系统运行正确，也能结合 CI、自动化测试和安全检查。这个思路如何？”

讨论将其转化为可实施的严格命题：**架构图不直接证明现实系统正确；架构图可以成为可执行工程契约和验证证据的统一入口。** 连接设计架构、实际代码架构、运行架构，并为节点和连线绑定测试、验证规则、源代码、构建来源与环境。

约定了设计视图、实现视图、运行视图三者对照；把未验证、失败、证据过期与已通过严格区分；提出通过 CI、E2E、权限测试、OPA/形式化方法、运行遥测来支持受限的性质证明。

**演化意义：**`Architecture Diagram → Executable Architecture → Proof-Carrying Architecture`。

### E02 — 用户提出“实时、发展、完全回放”

**用户原话：**“而且是实时动态的发展的，完全重现和回放整个开发过程”。

这使产品超越可执行架构，转向**软件研发过程数字孪生、工程黑匣子与时间机器**。讨论新增：事件采集、时间轴、状态重建、过程回放、因果 DAG、多 Agent 并行轨迹、历史分叉与可控重演。

严格区分三种能力：

1. **可视化回放**：还原已采集的架构/界面/动作/测试轨迹；
2. **状态重建**：由事件、源码版本和快照重建历史状态；
3. **执行重演**：在隔离且依赖受控的环境中重演工作流，比较结果，绝不重复生产副作用。

**演化意义：**`Executable Architecture → Temporal / Replayable Engineering System`。

### E03 — 用户提出区块链与独立立项

**用户原话：**“完全赞同你的想法，能吸收区块链的思想么，这个项目必须单独立项吧？”

形成初步共识：**独立项目、独立仓库、Rust 核心、独立 CI 与发布，但第一个真实集成对象是 DevControl / EngineeringOS。** 借鉴区块链的可核验证明而不默认自建链或发币。

重点吸收：追加式事件日志、哈希链、Merkle 承诺、签名、独立见证、因果 DAG、可执行验证政策。保留多个信任层级：本地账本 L1、独立见证 L2、外部公证 L3。

**演化意义：**`Replayable Engineering System → Independently Verifiable Engineering History`。

### E04 — 用户要求跨界探索，最后收敛

**用户原话：**“脑洞需要大开，可以连接更多的新鲜和跨界技术来进行迭代思考，最后再收敛看看”。

对话发散到：透明日志、航空黑匣子、双时态数据库、数字孪生、科学实验方法、形式化验证、故障注入、CRDT / local-first、数据血缘、因果推断、进化搜索、零知识证明和增量计算。

进一步设想：Google Earth 式可缩放软件宇宙；每次变更的 **Engineering Passport**；“平行宇宙”工程实验；架构图自动产生验证义务；跨聊天室/跨 Agent 工程记忆；自动探索候选架构方案。

**演化意义：**`Verifiable History → Engineering World Model + Experimentation`。

### E05 — 讨论收敛为三个内核和三个产品层

选择以 **Event、Evidence、State、Causality、Invariant、Experiment** 六个基本对象表达统一工程世界模型。以 **Evidence Kernel、Twin Kernel、Experiment Kernel** 为能力划分；产品侧分为 Chronicle、Universe、Intelligence 三层。首期以实用价值和可证明交付优先，避免一开始做全套前沿能力。

**演化意义：**产品独特性不在漂亮的图、单点 CI 或聊天记录，而在统一、可验证、可查询、具有时间和因果语义的工程世界模型。

### E06 — 用户宣布将本次讨论列为“创世纪”

**用户原话：**“请详细的保存我们的探讨，这也是工程历史的一部分，创世纪”。

由此要求**连思想形成过程也成为工程历史的组成部分**。本档案正是该理念的第零次实践：清楚保留思想来源、演化节点、尚待验证的方案、决策状态、存档摘要与未来接续路径。

**重要限制：**本文件是人工/AI 根据当前完整可见讨论整理的归档，不等于独立采集的逐字、逐毫秒、密码学签名聊天原始记录。不能宣称具备尚未实现的 Chronicle 完整性保证。

## 2. 创始原则（Founding Principles）

| ID | 原则 | 具体含义 |
|---|---|---|
| FP-01 | Delivery First | 每一步必须产生可以检验的工程产物，而非仅仅设计愿景。 |
| FP-02 | Evidence-based Done | 结论必须绑定代码 SHA、验证规则、执行环境及真实结果。 |
| FP-03 | Fact ≠ Claim | Agent 的“已修复”陈述不是测试通过；签名不是事实真实性。 |
| FP-04 | No Silent Rewrite | 已承诺的事件不得被静默覆盖；修正以新事件表达。 |
| FP-05 | No Evidence ≠ PASS | 缺失、过期、来源不明的证据必须显示 UNKNOWN/STALE，而非绿色。 |
| FP-06 | Replay without Side Effects | 回放和实验不能再次触发真实支付、交易、邮件、发帖、生产部署等副作用。 |
| FP-07 | Historical Honesty | 未采集的操作必须显示缺口，不靠 AI 臆造历史。 |
| FP-08 | Time and Causality are Different | 发生时间、接收时间、提交顺序、因果父节点是不同语义。 |
| FP-09 | Privacy by Design | 秘钥脱敏、最小采集、数据分层、保留期限和合法删除从第一版设计。 |
| FP-10 | Independent Verification | 必须有可审计、可离线运行的小型验证器，不能让主平台独自给自己背书。 |
| FP-11 | Open Protocol / Low Coupling | 独立仓库、统一事件协议，DevControl 只是第一个消费者。 |
| FP-12 | Small-step Evidence | 单阶段小闭环，真实集成验收后才扩张，杜绝假阳性。 |

## 3. 核心世界模型：六种一等对象

- **Event**：来源、参与主体、动作、时间、前驱引用、关联 ID、状态变化意图与真实产出。
- **Evidence**：测试日志、构建证明、签名、对象摘要、运行追踪、截图/回放资产等；包含真实性边界、采集方式与验证方法。
- **State**：在确定历史边界下投影出的项目状态、代码、架构、任务、测试门禁和运行部署状况。
- **Causality**：`causation_id`、父事件集合、任务/trace/commit/PR 关联、多 Agent 分支与合并关系，避免把时间先后误认为因果。
- **Invariant**：架构、权限、安全、数据、发布和流程必须持续满足的约束，必须声明验证方法及适用范围。
- **Experiment**：从已验证的检查点派生的隔离执行/模拟/比较；必须与事实账本区分，不能把实验结果伪装成生产历史。

建议追加语义标记：`OBSERVED`（来源已知的观察）、`ATTESTED`（经签署的陈述）、`VERIFIED`（已按某版本规则核验）、`INFERRED`（推断）、`UNKNOWN`、`STALE`、`FAILED`。状态并不互斥，应以 schema 细化，不应仅依赖一个颜色字段。

## 4. 三层内核与接口边界

### 4.1 Evidence Kernel — 可验证工程证据内核

- 采集、去重、事件持久化、增量哈希承诺、Merkle 批次、签名与检查点。
- 关联源码、构建、测试、部署和运行结果；形成来源明确的 Engineering Passport。
- 自证内容完整性，不替代对运行行为的独立验证；允许离线复核检查点。
- 可选见证/外部锚定；不能把单机哈希链等同于不可篡改，更不能把数据签名等同于真实性。

### 4.2 Twin Kernel — 实时/历史工程数字孪生内核

- 根据事件形成需求图、Agent 协作图、代码/接口关系、CI 测试图和部署运行图。
- 统一架构的设计、实现、运行三个视图；支持增量刷新与差异分析。
- 多时间语义、因果 DAG、快照、时点状态重建、历史查询、UI 时间轴、跨 Agent 长期工程记忆。
- 每个界面状态显示事件来源与证据置信边界，缺口显式标记。

### 4.3 Experiment Kernel — 隔离工程实验内核

- 从历史检查点创建独立实验宇宙，不覆盖真实历史。
- 支持确定性模拟、故障注入、候选修复、测试质量验证及多目标方案比较。
- 生产副作用必须被禁用、拦截、替换为模拟对象或经策略授权；所有实验记录写入独立命名空间。
- 可研究架构搜索/进化优化，但不能擅自批准生产部署。

### 4.4 分层产品形态

1. **Chronicle**：开放采集 SDK、事件协议、证据/时态内核、CLI/API、验证器。
2. **Universe**：实时架构图、空间缩放、时间轴、回放、证据面板、因果查看器。
3. **Intelligence**：历史学习、自动生成验证义务、反事实方案对比、安全实验建议。

架构图引擎可从 Archify 思想或适用开源实现借鉴，不预先绑定单一供应商和许可证。

## 5. 区块链思想的正确吸收边界

**推荐：**追加式事件记录、确定性编码、哈希链、Merkle 包含/一致性证明、Ed25519 签名、签名检查点、独立见证、多副本备份、外部公证接口。

**明确不做为首发依赖：**自建公链、挖矿、代币、经济激励、智能合约虚拟机、全网共识、高成本链上写入。

三个渐进可信度层：

- **L1** — 本地持久可验证账本；能检测已承诺历史被修改，但若不存在外部检查点仍可能遭遇整段重写。
- **L2** — 不同独立信任域的多节点见证签名根；检测对过去检查点的冲突或回滚。
- **L3** — 独立第三方透明日志或时间戳服务锚定重要检查点，按商业/合规需求实施。

事件内容、源代码和 Agent 输入输出默认不上公链；公开时只考虑最小承诺。泄露秘密不能靠“上链不可改”来挽回；把隐私与删除要求纳入数据生命周期。

## 7. Engineering Passport — 可验证交付护照

每一个需要交付的软件变更，应能以独立可核验的材料关联：

1. 需求和设计版本；
2. 参与开发的 Agent/人类身份及权限（隐私可控）；
3. 精确 Git Commit、PR、变更范围及代码来源；
4. 构建环境、依赖、镜像、产物摘要；
5. 测试和安全策略的版本、执行器及执行日志；
6. 已证明的性质、失败项、未知项和明确未覆盖的风险；
7. 部署目标、部署产物身份、可回滚信息；
8. 证据摘要、签名和审计验证器结果。

**发布门禁原则：**合格并不等于“所有测试绿”；必须依赖预先声明的准入政策以及证据覆盖面。已生成但未经审核的测试不能代替独立审查；Agent 不能无授权修改安全门槛。

## 8. 真正的全程回放需要怎样的数据

采集通道至少覆盖：需求/会话决策摘要、Agent 工具调用、Git 变更、PR/Review、CI 作业、测试、架构变更、构建、发布、遥测、告警、故障、修复。具体是否保存对话原文、键盘流或浏览器快照，应有权限、脱敏和保留周期，不应默认无限采集。

必须支持三类不同保证：

- **Trace Playback**：仅重放实际记录过的动作与观察；
- **State Reconstruction**：精确恢复已记录和可寻址资产支持的状态，并标明未知；
- **Sandbox Re-execution**：隔离地重复运行已捕获版本和环境，记录非确定性输入、时间、随机数与外部调用模拟。

历史重建所依赖的原始产物若缺失，系统应报告无法重建，不得合成“等价事实”。重演结果与原结果不同时，应作为新的实验事实记录，而不是改写旧事实。

## 9. 技术形态、仓库和工程纪律

**建议独立仓库：**`engineering-chronicle`（本档案创建时未证实已创建）。

## 11. 安全、真实性与不可回避的威胁模型

- **数据完整性**不等于**真实性**：签名和哈希只保证来源声明与承诺内容，仍需可信传感/采集/独立测试。
- **本地哈希链**不等于绝对不可篡改：可信锚点、审计见证、密钥隔离和强制留存策略必须按威胁模型设计。
- **完整日志**与**隐私保护**存在张力：禁止默认采集 SSH 私钥、API Token、支付密钥、客户个人信息；日志脱敏、加密、分级授权、保留期、合法删除机制必须首版考虑。
- **时间不是因果**：分布式乱序、晚到事件、重投、并发冲突不能用单时间戳硬凑单线故事。
- **AI 生成的测试**也会有错误：需要独立规则源、测试污染防护、变异测试和必要的人类审批。
- **实验不是生产事实**：所有分叉试验必须有环境边界和标识，不得自动写回事实账本成为原历史。
- **审计系统自身会失败**：需要小型独立验证器、灾难恢复测试、签名密钥轮换以及审计审计者的独立机制。
